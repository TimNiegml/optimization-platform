# 代码 → 耦合画布

把代码变成“可解释步骤 + 可运行画布 + 缺口清单”，不要把不支持的能力伪装成已有节点。

## 工作流

1. 获取代码、入口函数、期望结果、会话 ID（默认 `default`）；不要索取代码中的真实密钥。
2. 静态梳理：列出输入 `x`、测量 `y`/矩阵、硬件读写、算法、状态、分支、循环、停止条件、安全限制和输出。
3. 用 `list_algorithms`、`get_default_vocs` 核对平台真实能力；若要修改现有画布，再用 `get_canvas(session)`。
4. 按 [mapping.md](references/mapping.md) 映射 graph IR。固定次数循环必须用 `for_loop`，不得靠复制节点假装循环。
5. 将元素分为：`直接映射`、`需配置`、`平台缺失`。未知算法名绝不写入可运行 graph。
6. 先向用户展示映射草案。用户认可后，才用 `push_to_canvas(graph, session, note=...)` 推送可运行部分。
7. 对每个缺失元件按 [gap-template.md](references/gap-template.md) 输出规格，并生成一段可直接继续对话的“平台修改提示词”。只有用户明确要求实施时才改仓库。
8. 推送后用 `get_canvas` 回读核对；需要执行时再用 `run_workflow`，不要默认操作真实硬件。

## 固定输出

保持简短，依次给出：

1. **代码步骤**：编号、对应函数/行、输入、动作、输出。
2. **画布映射**：步骤 → 节点/边；标注分支与循环。
3. **缺失元件**：缺什么、为什么、可否先替代。
4. **下一步**：给出“推送画布”或“修改平台”的单一明确选择。

## 约束

- 代码信息不足时明确写“推断”，并只问一个最关键问题。
- 不执行代码中网络、设备、文件删除等副作用来理解代码。
- `for_loop` 节点使用 `data.iterations`；从它发出的边分别带 `role: body`、`role: exit`；循环体末端连回该节点。
- 条件循环继续使用条件回边并设置访问/步数上限；不要误转成固定次数循环。
- 保留源代码到节点的可追溯关系，方便用户点画布时回看代码含义。
